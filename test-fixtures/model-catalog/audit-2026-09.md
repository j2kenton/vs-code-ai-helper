## Availability policy

### Asymmetric evidence rule

Presence proves availability for that capture only: a model listed by a CLI
or an official page is available on the auth path and account tier that
produced the listing, on the capture date. Absence proves nothing beyond the
capture. A different account, plan, region or path class may see a different
list.

### Rule for adding

Add a model only when CLI output or an official provider page confirms its id
for the provider's default path. Record ids that are announced only, "TBD
client version", invitation-only, or account-specific (for example the
`*-contributor-free` Zen ids) as `not-added` with a reason. Presence on one
provider's catalog (for example Zen listing a `gpt-*` id) is not evidence that
another provider's CLI accepts it.

### Rule for removing

Remove an id only with one of three evidence kinds, recorded on the manifest
`removed` entry:

- `documented-retirement`: the provider documents the retirement, for every
  path class through which we offer the id.
- `universal-catalog`: the source is an entitlement-independent catalog, with
  a citation saying why (it is not fetched per account).
- `all-path-classes`: captures from every `supportedPathClasses` of the
  provider, each recorded.

A single account capture, an unauthenticated listing, a wrong-tier listing or
a failed local probe is only supporting context. Ids that fail the standard
are kept, as `verified-conditional` (with a label qualifier) or `unverified`.

### Conditional rule

When an id is confirmed for some path classes but not the default one, keep it
with an unchanged id and a label qualifier such as `(API key only)`. The
manifest entry is `verified-conditional` and carries the `qualifier`.

### Tier and plan restrictions

An id restricted to a plan or org tier (Copilot plan limits, invitation-only
access) is not removed for being unavailable on some accounts; the caveat goes
in the manifest entry as context.

### Copilot rule

Copilot has no CLI listing: its models come from the VS Code LM API at run
time. Its seeded "catalog" is the `COPILOT_MODEL_VARIANT_RULES` slug table, so
its manifest record covers those slugs, taken from GitHub's official
supported-models page. Rollout caveats (client version TBD, plan or org limits)
are context, not grounds for skipping an entry.

### Free-label rule

A model name carries a free marker (`(Free)` or the standalone word `Free`) if
and only if its `<ProviderId>:<baseModelId>` is in `VERIFIED_FREE_MODEL_IDS`,
and that id has an explicit manifest entry with a seeded status and a dated
`free` field (source plus verification date). The rule applies to base entries
and every effort variant, and only to blocks whose record sets
`freeLabelsAudited: true`; other blocks stay frozen by their existing
deep-equal pins until audited. Without dated $0 evidence, the marker is
removed (`relabelled` entry; for parsed catalogs the seed builder strips it and
the id is listed in `STRIPPED_FREE_MARKER_IDS`).

### Non-picker rule

Blocks the picker never offers (the `external` slice of the OpenCode catalog:
`github-copilot/*` and `openai/*`, kept only so saved selections resolve) are
`scope: "non-picker"` records with a reason. They carry no entries, are exempt
from correlation, are never in the free allowlist, and the drift script
ignores their ids (counting them).

### Saved selections

For each removed or renamed id, one of three outcomes (the `savedSelection`
field):

1. Renamed: a `legacyModelAliases` entry (listing each effort variant if alias
   keys do not match `@effort` suffixes; to be checked in Part 1).
2. Retired with a provider-documented same-cost-class replacement: an alias
   with the cited source.
3. Otherwise: preserve the stored id and rely on `Unknown model: <id>` plus
   the loud run-time failure.

A removed free id is never aliased to a paid id (for example
`deepseek-v4-flash-free` must not map to `deepseek-v4-flash`).

### Redaction rule

Strip credentials, API keys, account identifiers, e-mail addresses and
token-bearing URLs from every pasted CLI output. Record only the
authentication class (for example `Zen API key, standard tier`).

## Manifest schema summary

- Top level: `version`, `auditDate`, `policy`, `providerContext`,
  `humanScopeWaivers`, `records`.
- Record: `provider` (a real `ProviderId`), `block` (required only for
  providers with more than one block, i.e. `opencode-cli` with `opencode-go`,
  `opencode`, `external`; every other provider's record omits it and the
  loader resolves it to `default`), `scope`. Picker records also carry
  `defaultAuthPath`, `supportedPathClasses` (must equal the manifest's
  `providerContext` for that provider), `evidence` (`authContext`,
  `cliVersion`, `source` = exact command or official URL, `date`), `coverage`,
  `freeLabelsAudited` and `entries`. A snapshot object carries `command`,
  `cliVersion`, `capturedAt`, `authContext`, `catalogAuthority` (and `citation`
  when entitlement-independent). A `free` field is `{ source, date }`.
- The manifest itself requires `version`, `auditDate`, `policy`,
  `providerContext`, `humanScopeWaivers` and `records`, each type-checked;
  nothing is defaulted.
- Entry: provider-local base id (no provider prefix, no `@effort`, no `+fast`)
  and a status: `verified`, `added`, `relabelled`, `verified-conditional`,
  `unverified` (seeded), or `removed`, `not-added` (not seeded). A snapshot
  record covers seeded ids in its block that have no entry; an explicit entry
  always wins.

## The two contributor-free ids

The plan asks whether any account can select
`muse-spark-1.2-contributor-free` and `muse-spark-1.3-contributor-free`.

Both are present in the CLI capture at $0 and in the universal endpoint. But
OpenCode's Zen documentation names **six** permanently free models —
`Big Pickle`, `MiMo-V2.5 Free`, `Ling 3.0 Flash Fin Free`,
`Nemotron 3 Ultra Free`, `Nemotron 3.5 Lightning Free` and
**`Muse Spark 1.3 Contributor Free`** — and states that the Muse Spark
contributor model requires granting permission to use your work for model
improvement.

So:

- **`muse-spark-1.3-contributor-free`** — documented, but contributor-gated.
  Consent is a per-account condition, so this is `verified-conditional` with a
  qualifier, NOT an unconditional free entry.
- **`muse-spark-1.2-contributor-free`** — **`not-added`.** It is in the
  catalog and priced at $0, but it is not among the six the documentation
  names, so there is no official page confirming any account can select it.
  This is exactly the case the policy's own "Rule for adding" cites.
- **`jev-1.13-free`** — $0 in the CLI capture and present in the endpoint, but
  also not among the documented six. Record the $0 evidence and the
  documentation gap together rather than adding it to `VERIFIED_FREE_MODEL_IDS`
  on CLI cost fields alone.

Documentation count (6) and CLI $0 count (8) disagree. The disagreement itself
is the finding; it is not resolved by either source alone.
