Each has a `not-added` path disposition with its reason in `audit-2026-09.json`. This is not a claim the provider cannot offer the model; the policy adds an id only on a confirming capture, and another provider's catalogue is not one.
- **Not added, no evidence either way (owner decision, 2026-09-27):** OpenCode Go (the 2026-09-27 capture used a Zen key only), Antigravity, Kiro, Cline (hardcoded ClinePass seed, no discovery) and DevPass, each for both GPT-6 and Opus 5.5. Each is a policy-supported `not-added` path disposition with the rationale "no evidence the provider offers GPT-6 or Opus 5.5"; where the path discovers models live (Antigravity, Kiro, DevPass) the reason adds that discovery will surface such a model once the provider offers it. Their seeds are unchanged. Gathering evidence is not part of this task, and this is not a claim the provider cannot offer the model. No path is left `unverified`; `modelCatalogAudit.test.ts` asserts that.
- **Where the per-path outcome lives:** the manifest's `pathDispositions` array records every in-scope path and both families (`added`, `available-via-discovery` or `not-added`). No path is `available-via-discovery`: that status needs a live capture showing the path already surfaces the model, and none exists.
- **Invalid efforts:** `parseCodexModelSelection` and the Claude parser now throw for an effort outside the ladder; `cliAgentRunner` catches a `buildArgs` throw and reports it as a transport failure, so a bad saved selection fails visibly instead of reaching `--model` as `id@effort`.
